# ☢️ Project Guidelines & Architecture Manifesto
**Домен:** Высокопроизводительная Монте-Карло симуляция для медицинской физики (ОФЭКТ, ПЭТ, гамма-камеры, воксельные фантомы).

## Часть 1. Архитектурное устройство (Architecture Layout)

### 1.1. Data-Oriented Design (DoD) и Structure of Arrays (SoA)
Система работает в условиях экстремальных требований к производительности. Традиционное объектно-ориентированное программирование (ООП), где «частица» — это объект с методами, **строго запрещено** в вычислительном контуре.
*   Все физические данные (координаты, импульсы, энергия, состояния) представлены в виде плотных одномерных массивов (NumPy 1D Arrays), организованных по принципу **Structure of Arrays (SoA)**.
*   Вместо динамического выделения памяти используется **Pre-allocation** (предварительная аллокация). Буферы (`ParticleBank`, `KinematicState`, `InitialState`) создаются один раз при запуске. Текущее состояние отслеживается с помощью мутируемых курсоров (массивы размером 1 — `NDArray[Index]`).

### 1.2. Изоляция пайплайнов (Separation of Concerns)
Жизненный цикл программы четко разделен на две фазы: **Сборка (Setup/Static)** и **Симуляция (Compute/Runtime)**.
*   **Сборка (ООП-фаза):** Пользователь и конфигураторы оперируют Unified Scene Graph (через `CompositeNode`, `Volume`, `Source`). Здесь разрешено ООП для вычисления матриц трансформации, иерархии и подготовки данных.
*   **Компиляция (Flattening):** Перед стартом `SimulationManager` вызывает компиляторы (`GeometryCompiler`, `PhysicsCompiler`), которые «сплющивают» ООП-иерархию в плотные DOD-буферы (например, `FlattenedScene`).
*   **Симуляция (Runtime-фаза):** Итерация ООП-структур (графов, узлов) в вычислительном цикле **строго запрещена**. Numba-ядра (транспортные пропагаторы) ничего не знают о Python-объектах, они принимают только плотные массивы, сырые адреса памяти (C-pointers) и идентификаторы.

### 1.3. Безопасный многопоточный I/O и Data Handlers
Генерация случайных чисел (RNG) и сохранение результатов (HDF5) работают в режиме мультипроцессинга (`multiprocessing.Pool`).
*   Ветки RNG строго инициализируются через `numpy.random.SeedSequence` для каждого процесса во избежание корреляции сэмплов.
*   Менеджер данных (`DataManager`) работает как шина событий (Event Hub). Данные сериализуются путем заморозки массивов (`ndarray.flags.writeable = False`). Запись в HDF5 защищена блокировками (`Lock`, Mutex) и оборачивается в цикл `_write_with_retry` для безопасного конкурентного доступа макро-потоков.

## Часть 2. Правила написания кода (Coding Manifesto)

### Правило 1. Массивы и SoA вместо Объектов
Вычисления должны использовать логические маски над плотными массивами. Numba-ядра должны вызываться IN-PLACE для подмножеств индексов, отфильтрованных на стороне Python. Никакой фильтрации внутри Numba.

✅ **Как надо (DOD & SoA):**
```python
# Структура данных наследуется от NamedTuple с фабричным методом allocate
class KinematicState(NamedTuple):
    is_active: NDArray[Bool]
    position_x: NDArray[Float]
    # ...
    cursor: NDArray[Index]

    @classmethod
    def allocate(cls, capacity: int) -> "KinematicState":
        return cls(
            # ВСЕГДА используем явное указание dtype (см. Правило 6)
            is_active=np.zeros(capacity, dtype=np.bool_),
            position_x=np.zeros(capacity, dtype=Float), # Используем глобальные алиасы
            cursor=np.zeros(1, dtype=Index)
        )
```

❌ **Как не надо (ООП подход в Runtime):**
```python
# Грубейшее нарушение архитектуры!
class Particle:
    def __init__(self, x, y, z):
        self.x = x
        self.y = y
        self.z = z

for particle in particles:
    if particle.is_active:
        particle.propagate() # Нарушение: вызов методов объекта в цикле
```

### Правило 2. Физическая и размерная строгость (`hepunits`)
Никаких "магических чисел" и неявных размерностей. Использование констант из `hepunits` обязательно во всех физических формулах и при инициализации предметной области. Для входных данных из конфигураций (YAML/JSON) применяется Edge Parsing (конвертация строк вида `"140.5 keV"` в базовые единицы строго на этапе валидации `pydantic`).

### Правило 3. Строгие Контракты и Отказ от Duck Typing (Fail Fast)
Используем `isinstance`, Type Hints и `.pyi` стабы. Программа должна падать немедленно при неверных типах (`TypeError`).
**Запрет на `assert`:** Инструкции `assert` удаляются при запуске Python с оптимизацией (`-O`). Для валидации входных контрактов использовать только явные проверки `if not`.

### Правило 4. Композиция вместо наследования
При разработке компонентов, описывающих физический мир (Источники, Геометрия), сложные объекты строятся не через многоуровневое наследование, а через внедрение зависимостей (композицию). (Например, `Source` инстанцируется с конкретным `spatial_distribution` и `energy_spectrum`, а не наследуется в `CylindricalSource`).

### Правило 5. Numba и Оптимизация (Правила ядра)
Любой код внутри `@njit` обязан подчиняться следующим правилам:
1. **Минималистичные сигнатуры:** Принимаем только нужные 1D массивы, а не громоздкие `NamedTuple` целиком для улучшения cache locality.
2. **Zero Allocations (Никаких аллокаций):** Строгий запрет на создание массивов (`np.empty`, `np.zeros`) внутри Numba-ядер в основном цикле. Все промежуточные буферы (scratchpads) должны пре-аллоцироваться на стороне Python и передаваться в ядро по ссылке для in-place мутаций.
3. **Разрешен `fastmath=True`:** Для симуляций Монте-Карло этот флаг позволяет агрессивные LLVM оптимизации и векторизацию. Однако он отключает строгую проверку NaN/Inf (IEEE 754), поэтому входящие данные из Python должны быть очищены до вызова ядра.
4. **Защита от Infinite Loops:** Никогда не использовать `while True` без счетчика аварийного выхода (`max_steps`) в Woodcock tracking или rejection sampling, чтобы избежать мертвого зависания процесса.
5. **Дискретизация сетки:** Координаты, сопоставляемые с индексами вокселей, строго вычисляются через `math.floor()` перед кастом в `int`, иначе `int(-0.5)` вернет `0` вместо `-1`.
6. **Отладка:** Использовать **Sniper Prints** с жестким пространственным условием и выключать JIT (`NUMBA_DISABLE_JIT=1`).

✅ **Как надо (внутри Numba ядра):**
```python
from numba import njit
import math

# Включаем fastmath для вычислительных ядер, заранее гарантируя отсутствие NaN на входе
@njit(cache=True, fastmath=True)
def update_particle_positions(active_indices: np.ndarray,
                              pos_x: np.ndarray,
                              dir_x: np.ndarray,
                              step: np.ndarray):
    # Никаких np.empty внутри ядра!
    for i in range(active_indices.size):
        idx = active_indices[i]
        pos_x[idx] += dir_x[idx] * step[idx]

@njit(cache=True)
def rejection_sample_position(max_steps: int) -> float:
    steps = 0
    while steps < max_steps: # Безопасный цикл, избегающий глухого зависания
        # Логика сэмплинга...
        if success:
            return value
        steps += 1
    # Фоллбэк логика при исчерпании лимита
    return -1.0
```

### Правило 6. Управление точностью (Precision Policy)
В физике частиц выбор между `float32` и `float64` критичен как для скорости, так и для потребления памяти.
*   **Запрещено использование дефолтных типов** без явного указания в функциях создания массивов.
*   В системе должны использоваться глобальные алиасы типов (например, `Float` / `Index` / `Bool` на уровне ядра, или `hepp_float`, `hepp_energy`). Это позволяет легко переключать точность всей симуляции при необходимости.

✅ **Как надо:**
```python
# Явное указание типа через глобальный алиас проекта
energy_buffer = np.zeros(capacity, dtype=Float)
mask_buffer = np.ones(capacity, dtype=np.bool_)
```

❌ **Как не надо:**
```python
# Нарушение: неявный каст, непонятно, будет ли это float64 или платформа-зависимый тип
energy_buffer = np.zeros(capacity)
```

**При генерации кода для данного проекта:**
1. **ВСЕГДА** проверяй, относится ли код к фазе инициализации/сборки сцены (Python OOP, Pydantic, Builder) или к фазе симуляции (Numba, NumPy arrays, DOD-buffers). Не смешивай их.
2. **ВСЕГДА** явно указывай тип данных при создании NumPy массивов (`dtype=Float`, `dtype=np.int32`, `dtype=np.bool_`). Никакого неявного каста типов или полагания на дефолтные типы ОС.
3. **НИКОГДА** не используй циклы `while True` без явного счетчика аварийного выхода (`timeout` / `max_steps`) внутри Numba-ядер (например, при Woodcock tracking или rejection sampling), чтобы избежать бесконечного зависания воркера.
4. **НИКОГДА** не создавай массивы (аллокация памяти `np.empty`, `np.zeros`) внутри Numba-ядер. Все буферы должны создаваться снаружи и передаваться как аргументы.
5. **НИКОГДА** не пиши методы `to_yaml()` или `serialize()` в доменных классах; используй паттерн Builder в `core/config/`.
6. **НИКОГДА** не используй списки/словари (`[]`, `{}`) для данных о частицах в рантайме. Используй предварительно аллоцированные 1D NumPy массивы и инкрементируемые курсоры (`cursor[0] += 1`).
7. **ВСЕГДА** используй `hepunits` для хардкода физических величин.
8. **ВСЕГДА** пиши `.pyi` stubs для новых классов и функций, поддерживая строгую типизацию.
9. **НИКОГДА** не используй `assert`. Пиши `if not condition: raise ValueError(...)`.
10. **ВСЕГДА** запускай тесты через `python3 -m unittest` и убедись, что переменная окружения `PYTHONPATH=.` установлена. Никакого `pytest` без необходимости.
