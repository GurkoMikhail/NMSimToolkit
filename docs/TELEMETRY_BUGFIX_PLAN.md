# План багфикса: Восстановление Runtime-трекинга частиц и физической телеметрии

## 1. Контекст и цели

При запуске симуляции в GUI (в частности, сценария `nema_1_cam.yaml`) в текущей версии не отображаются 3D-треки частиц, не накапливается 2D-проекция детектора и не строится энергетический спектр.

В ходе архитектурного аудита выявлен комплекс проблем:
1. **Критическая ошибка размерности активности** в генераторе сцены, приводящая к замедлению шага по времени на 9 порядков (симуляция фактически замирает во времени).
2. **Аналитический FOV-фильтр в `GuiStreamDataHandler`**, который подменяет физику Монте-Карло аналитическим окном в мировых координатах и отсекает детектор, смещенный в пространстве.
3. **Отсутствие передачи `sensitive_volume_ids`** из сессии симуляции в потоковый обработчик данных.
4. **Несоответствие размерностей энергии** (МэВ vs кэВ) при построении энергетического спектра.
5. **Гонка потоков (Race condition)** при остановке конвейера телеметрии.

**Принцип исправления:** В Monte Carlo симуляции исключаются любые искусственные аналитические ограничения поля зрения (FOV). Все отборы событий на детекторе производятся строго по физическому объёму (`sensitive_volume_ids`), так как экранирование свинцом и коллимация уже смоделированы в физическом пространстве сцены.

## 2. Детальная спецификация дефектов и способы устранения

### Баг 1 (Критический блокер): Ошибка единиц измерения активности источника
* **Файл:** `core/config/builder.py`, строка 211 (`_build_source`)
* **Причина:**
  Функция `_to_float(config.activity, target_unit='Bq')` через `pint` возвращает голое числовое значение в беккерелях (для 100 MBq это $10^8$). Однако класс `Source` и ядро транспорта `SimulationManager` работают в единицах `hepunits`, где базовой единицей времени является наносекунда (`ns = 1.0`), соответственно $1\text{ Bq} = 10^{-9}\text{ ns}^{-1}$.
  В результате в `Source` попадает активность $10^8\text{ ns}^{-1}$ вместо $0.1\text{ ns}^{-1}$.
  Шаг по времени в `SimulationManager._calculate_time_step`:
  $$\Delta t = \frac{N}{\text{activity}} = \frac{1000}{10^8} = 10^{-5}\text{ ns} = 10\text{ фемтосекунд}$$
  Для достижения `stop_time = 0.1 s` ($10^8\text{ ns}$) симулятору требуется $10^{13}$ шагов. Процесс симулирует микроскопические интервалы времени, треки не успевают дойти до детектора и не заполняют буфер.
* **Решение:**
  В `core/config/builder.py` умножить активность на единицу `units.Bq`:
  ```python
  import hepunits as units
  ...
  activity = self._to_float(config.activity, target_unit='Bq') * units.Bq
  ```

### Баг 2 (Принципиальная физическая ошибка): Аналитический FOV-фильтр в `GuiStreamDataHandler`
* **Файл:** `core/data/stream_handlers.py`, строки 142–163
* **Причина:**
  Обработчик применяет аналитическое ограничение поля зрения:
  ```python
  half_fov = self.fov_size / 2.0
  in_fov = (px >= -half_fov) & (px <= half_fov) & (py >= -half_fov) & (py <= half_fov)
  ```
  Это нарушает методологию Monte Carlo моделирования:
  1. Коллиматор и свинцовая защита уже физически присутствуют в геометрии сцены и отсекают паразитные кванты.
  2. Фильтрация происходит по мировым координатам `pos_x`, `pos_y`. В `nema_1_cam.yaml` гамма-камера смещена на $Y = 329.05$ мм, из-за чего абсолютно все попадания в детектор отсекаются условием $|py| \le 200$ мм.
* **Решение:**
  1. Полностью удалить параметр `fov_size` и фильтр `in_fov`.
  2. Отбор событий производить **исключительно** по `mask = np.isin(volume_id, list(self.sensitive_volume_ids))`.
  3. Для проецирования координат попадания в пиксели матрицы:
     * Получать локальные координаты на плоскости детектора через трансформацию сцены (или использовать локальные габариты кристалла детектора $W \times H$).
     * Либо передавать размеры кристалла детектора (`detector_size_x`, `detector_size_y`) и матрицу перевода в локальную систему координат детектора.

### Баг 3: Отсутствие передачи `sensitive_volume_ids` в `GuiStreamDataHandler`
* **Файл:** `gui/controllers/simulation_session.py`, строки 79–86
* **Причина:**
  При инстанцировании `GuiStreamDataHandler` в сессии не передаётся список идентификаторов чувствительных объемов (`sensitive_volume_ids=None`). Без него обработчик не может отличить взаимодействия в кристалле детектора от рассеяния в воздухе или фантоме.
* **Решение:**
  1. В `SimulationSession` при анализе сцены или конфигурации находить узел `Detector` (или `GammaCamera.detector`).
  2. Получать его скомпилированный `volume_id` из `GeometryCompiler` (или таблицы объемов).
  3. Передавать `{detector_volume_id}` в `GuiStreamDataHandler(sensitive_volume_ids=...)`.

### Баг 4: Несоответствие размерностей энергии в спектре
* **Файлы:** `gui/controllers/ipc_receiver.py` / `gui/views/results_viewer.py`
* **Причина:**
  В `InteractionBuffer` депонированная энергия `energy_deposit` хранится в единицах `hepunits.MeV` (для фотона 159 кэВ значение составляет `0.159`).
  `ResultsViewer.set_spectrum_data(energy_array, bins=120, max_energy=200.0)` ожидает значения в кэВ. Значение `0.159` попадает в самый первый канал $[0; 1.67]$ кэВ и выглядит как пустой график / шум около нуля.
* **Решение:**
  При эмиссии сигнала `spectrum_received` в `IPCReceiver` выполнять масштабирование в кэВ:
  ```python
  # energy_deposit в MeV -> переводим в keV для гистограммы
  self.spectrum_received.emit(edep * 1000.0)
  ```

### Баг 5: Остановка `IPCReceiver` до обработки финальных пакетов
* **Файл:** `gui/controllers/simulation_session.py`, строки 178–187
* **Причина:**
  При наступлении события `simulation_finished` немедленно вызывается `ipc_receiver.stop()`, который выставляет `_stop_event` и отправляет `'stop'` в очередь треков. Однако `DataManager` в этот момент может еще только вычитывать финальный `flush_interactions()` из очереди `SimulationManager`. Финальные треки и счета детектора теряются.
* **Решение:**
  Перед остановкой `ipc_receiver` дождаться опустошения очереди и завершения `DataManager`:
  ```python
  if self.data_manager is not None and self.data_manager.is_alive():
      self.data_manager.join(timeout=1.0)
  ```
  Дать `IPCReceiver` возможность дочитать оставшиеся элементы из `track_queue`.

### Баг 6 (UX для интерактивной отладки): Буферизация и покадровый сброс
* **Файлы:** `gui/controllers/simulation_session.py`, `core/transport/simulation_managers.py`
* **Причина:**
  При интерактивном запуске и особенно при пошаговом моделировании (`Step`) пользователь ожидает видеть треки сразу после каждого шага. Буфер на 100 000 взаимодействий накапливает данные пакетами по нескольку десятков шагов.
* **Решение:**
  В `SimulationSession` для интерактивного режима GUI инициализировать `SimulationManager` с адаптированной емкостью буфера (`buffer_capacity = max(self.particles_number * 2, 5000)`), либо добавить флаг интерактивного сброса, вызывающий `flush_interactions()` при наличии активных треков.

## 4. Критерии приемки (Verification Criteria)

1. **Тест шага по времени:** При загрузке `nema_1_cam.yaml` значение `dt` в симуляторе составляет $\sim 10\ \mu\text{с}$ (а не $10\text{ фс}$), шаги физики выполняются с адекватной скоростью.
2. **Отображение треков:** В 3D-вьюпорте сразу после старта появляются траектории фотонов, выходящих из фантома.
3. **Энергетический спектр:** В окне `ResultsViewer` на вкладке «Энергетический спектр» формируется пик полного поглощения в районе $159\text{ кэВ}$ (технеций/йод по конфигурации NEMA).
4. **2D-проекция:** В окне «2D Проекция детектора» накапливаются отсчеты, зарегистрированные кристаллом гамма-камеры, без искусственных срезов по краям.
